# Storage integrity and concurrency

Canonical files are UTF-8 raw Markdown/CSV/JSON/YAML in exactly one authoritative writable provider. Before mutation, fetch complete current content from one bound generation, verify instance/container/root scope, and record input hashes/revisions plus intended output hashes in a durable operation. Never mix Drive revisions and GitHub commits, mirror writes, automatically fail over, or use indexed/search excerpts as a replacement base.

Drive canonical objects are mapped by exact file ID and MIME type. Update the same ID with a proved precondition when exposed, then independently read back; native Docs/Sheets look-alikes are rejected.

GitHub canonical objects are bound by immutable repository ID, full canonical ref, root prefix, and exact base commit. Read the ref once, then address the base commit/tree/blobs immutably. When the operation lacks an intent record, publish that uniquely named immutable intent in a small non-force commit, verify it, and re-read the head before constructing outputs. Build all related canonical blobs and one tree, create a commit whose sole parent is the observed base, and move the canonical ref once with `force=false`. Re-read and verify the final ref, parentage, tree, and changed blobs. An object or orphaned commit is not completion. Valid manual commits are preserved as concurrent edits and revalidated from the fresh head; invalid, merge-history, or foreign-instance commits block canonical work. A sibling commit, unexpected head, branch-rule rejection, public/archive state, truncated tree, or oversized mutation also blocks publication. On conflict or lost response, reconcile reachable commits and the durable original intent before retry; never force, rewind, or delete the canonical ref.

GitHub activation additionally requires observed force-push/deletion protection, a trusted first-commit ancestry anchor, monotonic heads within each run, and observable retained-object size for the growth bound. Ordinary exact reads validate the bound instance/config and requested blob without downloading every wiki blob; canonical writes validate the complete current generation once per immutable head and cache that result only for the run. A legitimate repository rename blocks normal work until a current-user-authorized repair resolves the same immutable repository ID and atomically updates both locator bindings; host skill/task metadata is then verified separately.

V2 `SafeWriter.replace` requires the exact `FileSnapshot` used to generate the content as `base=`. Immutable intent and completion artifacts preserve original instance/target/base/output identity. Reusing an operation ID with another target/content/base conflicts. Completed replay returns `WriteReceipt.verified_sha256`/`verified_revision` for history and `current` for the currently observed target; it never rewrites later manual edits. Scope validation walks actual parent IDs for target, journal, inbox and backup destinations. Immutable creates reconcile paginated inventory and exact readback after lost responses.

The local strong Drive fake exposes conditional writes and idempotent creates; the deliberately weak fake has neither guarantee. Strict Drive mode blocks canonical changes on the weak adapter. Explicit Drive-only `best-effort-personal` mode may instead bind `SafeWriter` to a held `PermanentDriveLock`: one raw JSON file is retained forever, carries a unique owner plus acquisition/expiry timestamps, becomes reclaimable at exactly 20 hours, and is set to unlocked after work. `DailyRunStore` accepts its observed ownership receipt as a best-effort execution guard. GitHub requires the complete non-force commit/ref protocol and has no weak/best-effort mode. No fake establishes a real connector guarantee; live raw freshness, scheduled writes, and overlap acceptance remain separate evidence.

The permanent lock is intentionally not called atomic. Two simultaneous readers can both write themselves as owner, and a later write can invalidate an earlier readback. The helper therefore reads back, re-checks before every external call/write, refuses to release another owner, and fails closed on malformed timestamps. These measures reduce ordinary daily/weekly overlap for a personal instance but do not prove exact attempt budgets, idempotency, or lost-update prevention.

Cross-file transactions are not assumed for Drive. A qualified GitHub adapter uses one verified canonical-ref movement as the multi-file visibility point. Research/source records and wiki changes are verified before successful queue removal. Report publication retries are independent of research. Lost write responses are reconciled by operation ID, bound target/container/generation, and hash before retry.

Interactive and weekly inputs use unique command/proposal files when an exclusive canonical writer cannot be established. The single canonical writer rebuilds from fresh current projections plus durable inputs. Forced conflicts fail closed and retain inputs. Pagination is mandatory; partial indexed text is never a replacement base. Residual risk from arbitrary simultaneous manual edits remains a live acceptance item.
