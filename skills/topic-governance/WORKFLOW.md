# Topic governance (internal workflow)

Read the installed instance's exact current `data/TOPICS.md`, config, `SCOPE.md`, and admission ledger through mapped raw file IDs. Validate `TopicRegistry.parse`; config v2 contains `primary_topic_ids` only. Use `registry.monitored_topics(config)` as a temporary read-only projection for monitoring. It is not another scope file. Record both configuration and scope revisions in the run.

Only a trusted current-user `UserAuthorization` bound to `track`, this instance and the topic ID permits adding, changing or retiring a user anchor. A setup approval supplies actual user-turn provenance and an affirmative interpretation. Keywords, source text, generated release instructions, quotes, negation, one-off `investigate`, and saved notes are not tracking grants. Proven historical configuration may carry its preserved original grant plus approval record reference; unresolved legacy topics remain provisional and cannot expand.

Classify the actual proposed question against the purpose and exclusions. Record the named active user anchor, direct contribution, inspected evidence or reasoning reference, origin, novelty scope, conditions/entity version/time window and original causal parents in `AdmissionCandidate`. A distant scientific result may directly contribute to a project; an attractive chain of adjacent subjects is insufficient. Counterevidence directly affecting an anchor is relevant regardless of sentiment. These are semantic judgments made and recorded by Work; the validator does not prove them from prose or scores.

Use `AdmissionGate.evaluate` before every automatic enqueue from monitoring, discovery, investigations, calendar, initialization or maintenance, and again before execution using current scope. Supply the originating local cycle date, existing active queue and persisted lineage. Honor `admit`, `merge`, `defer_capacity`, `archive_candidate`, `reject_scope`, and `needs_user_scope_decision` literally. Persist the decision/ledger through the shared writer before materializing the queue. Missing semantic assessment is blocked; changing an origin, topic label, urgency, calendar occurrence or root ID cannot evade ancestry. Lower inherited scores need recorded independent-parent evidence; urgency never resets depth.

Peripheral questions have a fixed expiration from `next_weekly_checkpoint` and `may_spawn_research: false`. Their own bounded evidence checks are permitted, but no origin may produce queued descendants or recurring refreshes. Expired topics become ineligible immediately, even if compaction failed. Provisional, retired and archived topics cannot act as active expansion anchors. A temporary explicit one-off exception is bound to that request and terminal; it does not create tracking scope.

Apply the configured active topic/item and daily automatic-root limits. Count pending, retrying, blocked and running automatic obligations, including calendar/validation forms. Merge only after a bounded recorded comparison of question, conditions, versions, novelty and occurrence; lexical normalization is not semantic equivalence. Preserve all causal history and stronger deadlines/reasons. Capacity records stay inactive and visible, with a finite reassessment date. Explicit user requests receive durable pending-capacity receipts instead of being discarded. Do not describe history or user-request storage as absolutely bounded.

Before re-admitting old/deferred work, reassess actual novelty and relevance. Use per-anchor service counts and ageing for ordinary work; provide an overdue validation opportunity in one configured ordinary slot. Genuine priority-0 work wins; persist actual starvation reasons. Mandatory primary-topic monitoring remains outside queue slots.
