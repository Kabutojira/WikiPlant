# Mandatory daily main-topic refresh

For every user-configured primary topic, use `(instance_id, configured local date, topic_id)` as the durable key. Run before queue execution even when the queue is empty, exhausted, blocked, or temporarily unreadable, provided safe storage remains available. Reuse a verified completion; resume remaining query/source counters after interruption.

Derive the interval from the last successful check with configured overlap. Run varied current searches within the per-topic query cap, inspect the most material original evidence within the source cap, and compare it with stored claims, projects, constraints, and calendar. Record source/event dates so newly indexed old material is not called a new event. Save supported corrections/developments, implications, events, wiki changes, counters, coverage, and limitations.

Short verification needed to assess a monitored update belongs here. Distinct deep questions are deduplicated and queued with valid lineage; select at most three children for one pass and obey the automatic-root admission cap. Do not promote discovered entities to primary topics. A successful bounded search with no material result is `no_material_update`; an outage/cap/failed fetch is `partial` or `blocked`, never “no news.” This work class consumes zero queued-attempt slots.

Resolve configured `primary_topic_ids` through the current authoritative `TOPICS.md`; only active user anchors qualify. Use `PersistentMonitoringLedger` (or the identical verified host workflow) to persist a reservation before each tool invocation and the observed outcome afterwards. Record query text/result reference separately from fetch/inspection/source locator. A reservation is not a successful search. Unresolved or failed invocations require partial coverage and cannot advance `successful_watermark`; retain the unsearched interval. Challenge material conclusions within this pass's remaining source/query allowance. Every deeper candidate passes shared question-specific admission, including terminal ancestry and novelty checks.

Material findings require a saved raw `monitoring_assessment`, bound to the instance/topic/local date/key and exact coverage interval. Resolve every source by mapped file ID/hash and each inspected locator, claims/dependencies, challenges and finding coverage through `validate_monitoring_assessment`. Identify affected wiki pages; save the evidence before invoking the shared writer. Each wiki completion must bind its immutable intent to `workflow=monitoring`, this monitoring key, assessment reference and page ID. `run_daily(..., commit_monitoring=...)` independently checks those receipts. Missing evidence or merge proof retains a partial/pending result without a successful watermark; retry saved evidence/merge without repeating searches or resetting allowances. Report assessed claim status and limitations, never raw finding text as a verified development merely because a search returned.

The resource ledger's `finish(record, "complete")` deliberately remains partial for material findings until it receives `commit_receipts`. Wire `finalize_monitoring` to `ledger.finish(record, "complete", commit_receipts=receipts)` after the wiki commit, so the raw reservation ledger and daily completion agree. That method independently revalidates the assessment and receipts. If finalization is interrupted, the canonical run retains evidence and resumes the original wiki operation; neither a resource reservation nor a pre-commit coverage flag is a successful watermark.
