# Mandatory daily main-topic refresh

For every user-configured primary topic, use `(instance_id, configured local date, topic_id)` as the durable key. Run before queue execution even when the queue is empty, exhausted, blocked, or temporarily unreadable, provided safe storage remains available. Reuse a verified completion; resume remaining query/source counters after interruption.

Derive the interval from the last successful check with configured overlap. Run varied current searches within the per-topic query cap, inspect the most material original evidence within the source cap, and compare it with stored claims, projects, constraints, and calendar. Record source/event dates so newly indexed old material is not called a new event. Save supported corrections/developments, implications, events, wiki changes, counters, coverage, and limitations.

Short verification needed to assess a monitored update belongs here. Distinct deep questions are deduplicated and queued with valid lineage; select at most three children for one pass and obey the automatic-root admission cap. Do not promote discovered entities to primary topics. A successful bounded search with no material result is `no_material_update`; an outage/cap/failed fetch is `partial` or `blocked`, never “no news.” This work class consumes zero queued-attempt slots.
