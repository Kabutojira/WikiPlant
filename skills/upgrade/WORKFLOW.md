# Explicit instance update and recovery

Use for affirmative current-user “update”/“upgrade” intent, never scheduled consent or release-note instructions. Validate one instance, operation `update`, actual user-turn provenance and exact resolved release identity. If an update notice is selected, pin that notice's version/commit/digest; resolve “latest stable” once. Check-only requests use `check-updates` and remain read-only to runtime files.

Load `INSTANCE.json`, config, provider mapping/binding, the prior runtime's `source-manifest.json` and unfinished update intent from one exact generation. Verify prior manifest against config's digest and INSTANCE/config release/commit pins; derive rollback reader compatibility from those bytes. Verify target source repository provenance, published release, detached manifest digest, compatibility/migrations, bounded allowlisted UTF-8 payload hashes and runtime dependency closure. An incomplete updater may recognize only its two pinned identities; ordinary research stays paused. Do not silently widen permissions or adopt a changed known release.

Use `Updater` immutable checkpoints and `docs/upgrades.md`. Inventory all affected mutable files and bindings; record exact generation snapshots and intended outputs before changing anything. Preflight tool exposure, customizations, pending operations, backup space and migration path. Pause only the two bound tasks and prove in-flight writers drained with actual host evidence. Continue to accept user submissions as durable intake.

Create and independently read back scoped backups. Stage a distinct runtime directory, preserving the old snapshot. Validate detached migrated bytes and explain counts, unresolved references, claim reassessments and scope decisions. Drive applies same-ID snapshot-bound writes and maps observed IDs for new files. GitHub commits the complete related path set plus checkpoint through one non-force canonical-ref update from the observed base and verifies ref/parent/tree/blobs. Preserve notes, scope, queue/calendar lineage and attempts, pending reports, archive/source references, language/timezone and task IDs. Do not rerun initialization or reset allowance.

Update the existing private installed skill through supported host controls. A changed provider object or GitHub commit is insufficient. Verify fresh invocation and inspect the actual task IDs/prompts. If update controls or safe task-identity preservation are unavailable, persist the precise blocked phase and prepared handoff. Do not fabricate host observations. Reconcile lost responses before repeating effects.

Before activation verify schemas, references, counts, all migrated raw hashes, read-only wiki query, archive lookup, installed binding and drained writers. Update bound INSTANCE/config pointers through snapshot-bound provider writes and independently verify their exact Drive IDs or GitHub committed paths, schema, instance/provider/root and release/commit/manifest identities. Resume the existing tasks and reconcile pending intake once. A failed activation readback requires recovery pause evidence or an explicit unverified-pause blocker. Save/read back the update report, publish native result and persist observed delivery state. Future scheduled execution and human notification receipt remain unknown until observed.

Rollback is permitted only with demonstrated reader/schema compatibility or a validated repair migration. Never restore a whole old backup over later research/intake. Keep incomplete recovery state. Export remains a private detached copy. Normal weekly/daily work never performs this update automatically. Changing Drive/GitHub provider is a separately authorized migration: pause/drain, snapshot/export, verify destination, update the existing skill/tasks, smoke-test, then activate. Keep the old store read-only; never mirror or automatically fall back.
